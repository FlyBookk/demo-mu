# 广告模块数据库变更说明文档

**文档版本**: v1.0
**创建日期**: 2026-01-20
**变更类型**: 表结构重构
**影响范围**: `t_advertising_data` 表
**风险等级**: 🔴 高（涉及表结构变更和数据迁移）

---

## 1. 变更概述

### 1.1 变更目标
对广告数据表 `t_advertising_data` 进行结构优化，支持详细的广告发票数据导入需求。

### 1.2 核心变更
1. **账单周期字段拆分**：`year_month` 拆分为 `billing_start_date` 和 `billing_end_date`
2. **新增发票详细字段**：发票状态、支付类型、广告活动、点击数据等 18 个新字段
3. **添加唯一索引**：`invoice_number` 字段添加唯一索引，支持去重
4. **优化索引设计**：新增 7 个索引，提升查询性能

### 1.3 变更前后对比

| 变更项 | 变更前 | 变更后 | 说明 |
|-------|--------|--------|------|
| 字段数量 | 14 个 | 30 个 | 新增 16 个字段 |
| 核心字段 | year_month (单一时间) | billing_start_date + billing_end_date | 双时间字段 |
| 唯一约束 | 无 | uk_invoice_number | 发票编号去重 |
| 索引数量 | 1 个 | 8 个 | 提升查询性能 |
| 数据粒度 | 月度汇总 | 发票明细 | 支持精细化管理 |

## 4. 数据迁移方案

### 4.1 迁移策略选择

#### 4.1.1 场景一：无历史数据
- **适用**：表中无数据或数据不重要
- **操作**：直接执行变更脚本，跳过迁移步骤
- **风险**：无

#### 4.1.2 场景二：少量历史数据（< 1万条）
- **适用**：数据量小，可接受短时间停机
- **操作**：使用脚本自动迁移
- **风险**：低
- **预计时间**：5 分钟

#### 4.1.3 场景三：大量历史数据（> 1万条）
- **适用**：数据量大，需要保留完整历史
- **操作**：分批迁移或手动迁移
- **风险**：中
- **预计时间**：根据数据量定

### 4.2 自动迁移脚本

打开变更脚本 `migration_advertising_optimize_20260120.sql`，找到第三步（数据迁移），取消注释并根据实际情况调整：

```sql
INSERT INTO `t_advertising_data` (
  `store_name`,
  `site_code`,
  `invoice_number`,
  `invoice_status`,
  `billing_start_date`,
  `billing_end_date`,
  `issue_date`,
  `currency`,
  `invoice_amount`,
  `cost`,
  `exchange_rate`,
  `amount_cny`,
  `attachment_path`,
  `remark`,
  `create_by`,
  `create_time`,
  `update_by`,
  `update_time`
)
SELECT
  CONCAT('迁移店铺-', site_code) as store_name,
  site_code,
  COALESCE(invoice_no, CONCAT('MIGRATED-', id)) as invoice_number,
  'PAID_IN_FULL' as invoice_status,
  STR_TO_DATE(CONCAT(year_month, '-01'), '%Y-%m-%d') as billing_start_date,
  LAST_DAY(STR_TO_DATE(CONCAT(year_month, '-01'), '%Y-%m-%d')) as billing_end_date,
  STR_TO_DATE(CONCAT(year_month, '-01'), '%Y-%m-%d') as issue_date,
  currency_code as currency,
  amount as invoice_amount,
  amount as cost,
  exchange_rate,
  amount_cny,
  attachment_path,
  remark,
  create_by,
  create_time,
  update_by,
  update_time
FROM `t_advertising_data_backup_20260120`;
```

- 业务方要求回滚

## 6. 风险评估与应对

### 6.1 风险矩阵

| 风险项 | 风险等级 | 可能性 | 影响 | 应对措施 |
|-------|---------|--------|------|---------|
| 数据丢失 | 🔴 高 | 低 | 严重 | 完整备份 + 测试验证 |
| 迁移失败 | 🟡 中 | 中 | 中等 | 准备回滚脚本 |
| 停机超时 | 🟡 中 | 中 | 中等 | 凌晨执行 + 充分测试 |
| 性能下降 | 🟢 低 | 低 | 较小 | 索引优化 |
| 应用兼容 | 🔴 高 | 中 | 严重 | 后端代码同步更新 |

### 6.2 应急预案

#### 6.2.1 数据迁移卡住
**现象**：迁移脚本执行超过预期时间
**处理**：
1. 检查 `SHOW PROCESSLIST` 查看进度
2. 如果长时间无响应，终止脚本
3. 执行回滚，调整迁移策略（分批迁移）

#### 6.2.2 唯一索引冲突
**现象**：`ERROR 1062: Duplicate entry for key 'uk_invoice_number'`
**处理**：
1. 查找重复数据：
```sql
SELECT invoice_number, COUNT(*) as cnt
FROM t_advertising_data_backup_20260120
GROUP BY invoice_number
HAVING cnt > 1;
```
2. 手动去重或调整迁移脚本

#### 6.2.3 应用报错
**现象**：应用启动后连接数据库失败或查询报错
**处理**：
1. 检查应用日志，定位具体错误
2. 如果是字段不存在，检查后端代码是否已更新
3. 如果无法快速修复，执行回滚
