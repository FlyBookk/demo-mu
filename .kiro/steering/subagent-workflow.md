# 子代理工作流规范

使用子代理（Subagent）执行独立任务，保持上下文隔离和任务专注。

## 子代理派发原则

### 何时使用子代理

✅ **应该使用子代理**：
- 执行 tasks.md 中的独立任务
- 需要隔离上下文的操作
- 批量执行多个任务
- 需要专注于单一目标的场景

❌ **不应该使用子代理**：
- 简单的信息查询
- 需要用户交互的操作
- 跨任务的协调工作

## 子代理派发流程

### 1. 读取任务列表

```markdown
# tasks.md
- [ ] 1.1 创建 UserDTO 类
- [ ] 1.2 创建 UserMapper 接口
- [ ] 1.3 实现 UserService.getUserById
- [ ] 1.4 添加单元测试
```

### 2. 标记任务为进行中

```
更新任务 1.1 状态为 in_progress
```

### 3. 派发子代理

```javascript
invokeSubAgent({
  name: "spec-task-execution",
  prompt: `
执行任务 1.1：创建 UserDTO 类

**目标**：创建用户数据传输对象

**文件**：domain/dto/UserDTO.java

**要求**：
- 使用 @Data @Builder @NoArgsConstructor @AllArgsConstructor
- 包含字段：id, name, email, createTime
- 遵循 QuickCEP 代码规范

**验证**：
- 编译通过
- 符合规范检查
  `,
  explanation: "派发子代理执行任务 1.1"
})
```

### 4. 等待子代理完成

子代理会：
1. 创建文件
2. 编写代码
3. 运行编译检查
4. 执行代码审查
5. 返回结果

### 5. 更新任务状态

```
更新任务 1.1 状态为 completed
```

### 6. 继续下一个任务

重复步骤 2-5，直到所有任务完成。

## 子代理上下文隔离

### 每个子代理获得的上下文

```
✅ 包含：
- 当前任务的详细描述
- 相关的设计文档
- QuickCEP 代码规范
- TDD 工作流规范
- 代码审查清单

❌ 不包含：
- 其他任务的执行细节
- 主对话的历史记录
- 无关的项目信息
```

### 上下文隔离的好处

1. **专注**：子代理只关注当前任务
2. **一致**：每个任务使用相同的规范
3. **可靠**：避免上下文污染导致的错误
4. **可追溯**：每个任务的执行独立可查

## 批量执行模式

### 串行执行（Kiro 默认）

```
任务 1.1 → 完成 → 任务 1.2 → 完成 → 任务 1.3 → 完成
```

**优点**：
- 任务有依赖时安全
- 可以及时发现问题
- 资源占用稳定

**缺点**：
- 执行时间较长
- 无法并行加速

### 分批执行（推荐）

```
批次 1（独立任务）：
  - 任务 1.1 创建 UserDTO
  - 任务 1.2 创建 OrderDTO
  - 任务 1.3 创建 ProductDTO
  ↓ 全部完成后
  
批次 2（依赖任务）：
  - 任务 2.1 实现 UserService（依赖 1.1）
  - 任务 2.2 实现 OrderService（依赖 1.2）
  ↓ 全部完成后
  
批次 3（测试任务）：
  - 任务 3.1 UserService 测试
  - 任务 3.2 OrderService 测试
```

## 子代理执行模板

### 标准任务执行

```markdown
## 子代理任务：{任务编号} {任务名称}

### 任务目标
{一句话描述}

### 文件操作
- 创建：`path/to/NewFile.java`
- 修改：`path/to/ExistingFile.java`

### 实现要求
1. {要求 1}
2. {要求 2}
3. {要求 3}

### 遵循规范
- QuickCEP 代码规范
- TDD 工作流（如需要）
- 代码审查清单

### 验证步骤
1. 编译通过：`mvn compile`
2. 测试通过：`mvn test -Dtest=XxxTest`
3. 代码审查通过

### 完成标准
- [ ] 功能实现完整
- [ ] 代码符合规范
- [ ] 测试全部通过
- [ ] 提交代码
```

### TDD 任务执行

```markdown
## 子代理任务：{任务编号} {任务名称}（TDD）

### TDD 流程

#### RED（写失败测试）
1. 创建测试文件：`XxxTest.java`
2. 编写测试方法：`test{Method}_{Scenario}_Should{Result}`
3. 运行测试，确认失败

#### GREEN（写最小实现）
1. 实现功能代码
2. 运行测试，确认通过

#### REFACTOR（重构优化）
1. 优化代码结构
2. 运行测试，确保仍然通过

#### COMMIT（提交代码）
```bash
git add .
git commit -m "feat: {任务描述}"
```

### 完成标准
- [ ] 测试先行
- [ ] 测试通过
- [ ] 代码优化
- [ ] 已提交
```

## 错误处理

### 子代理执行失败

如果子代理报告失败：

1. **分析失败原因**
   - 编译错误？
   - 测试失败？
   - 规范不符？

2. **决定处理方式**
   - 修复后重试
   - 调整任务拆分
   - 更新设计文档

3. **记录问题**
   - 更新任务备注
   - 记录解决方案

### 任务依赖问题

如果任务因依赖未完成而失败：

1. **检查依赖任务状态**
2. **先完成依赖任务**
3. **重新执行当前任务**

## 进度跟踪

### 任务状态

```markdown
- [ ] 未开始（not_started）
- [~] 队列中（queued）
- [-] 进行中（in_progress）
- [x] 已完成（completed）
```

### 进度报告

```markdown
## 执行进度

总任务数：10
已完成：3
进行中：1
待执行：6

完成率：30%
预计剩余时间：约 35 分钟
```

## 使用示例

### 单个任务

```
执行任务 1.1
```

Kiro 会：
1. 读取任务 1.1 详情
2. 派发子代理
3. 等待完成
4. 更新状态
5. 报告结果

### 批量任务

```
执行所有任务
```

Kiro 会：
1. 读取 tasks.md
2. 识别所有未完成任务
3. 按顺序派发子代理
4. 逐个执行
5. 汇总报告

### 指定范围

```
执行任务 1.1 到 1.5
```

Kiro 会：
1. 执行任务 1.1
2. 执行任务 1.2
3. ...
4. 执行任务 1.5
5. 停止并报告

## 最佳实践

1. **任务拆分要细**：2-5 分钟的任务最适合子代理
2. **明确依赖关系**：在 tasks.md 中标注依赖
3. **验证要具体**：给出明确的验证命令
4. **及时提交代码**：每个任务完成后提交
5. **保持专注**：一个子代理只做一件事
