# 报税汇总接口（tax-summary）配送数据关联分析

## 分析日期
2026-03-30

## 分析目标
确认配送数据中同一订单号关联多行记录时，报税汇总计算是否存在重复计算风险。

## 数据背景

以阿斯特店铺为例（120,962 条配送数据）：

| 指标 | 数值 |
|------|------|
| 总配送行数 | 120,962 |
| 唯一订单数 | 116,677 |
| 多行订单数（同一订单号出现>1次） | 4,019 |
| 多SKU订单数（同一订单号有不同SKU） | 3,611 |
| 分批发货订单（同一订单不同追踪编码） | 833 |

订单行数分布：
- 1行：112,658 个订单
- 2行：3,827 个订单
- 3行：147 个订单
- 4-8行：45 个订单

## 报税汇总核心逻辑分析

### 1. 收入总额计算（无重复风险 ✅）

```java
// 逐行遍历配送数据，累加 totalAmount
for (ShippingData shipping : allShipping) {
    // 按发货日期筛选本季度
    BigDecimal amount = shipping.getTotalAmount();
    totalRevenue = totalRevenue.add(amount);
}
```

收入总额直接遍历配送数据逐行累加。每行配送记录对应一个独立的 SKU 行项，金额互不重叠。同一订单的多行记录（不同 SKU）各自有独立的商品价格、税费等，累加是正确的。

**结论：收入计算不存在重复问题。**

### 2. 配送订单号集合构建（无重复风险 ✅）

```java
Set<String> shippingOrderIds = new HashSet<>();
for (ShippingData shipping : allShipping) {
    if (在本季度范围内) {
        shippingOrderIds.add(shipping.getOrderId());
    }
}
```

使用 `Set<String>` 收集订单号，天然去重。同一订单号无论在配送数据中出现多少行，集合中只保留一个。

**结论：订单号集合不存在重复问题。**

### 3. 销售数据关联（需关注 ⚠️）

```java
// income 类型销售数据：订单号在本季度配送集合中
List<SalesData> incomeList = allSalesData.stream()
    .filter(s -> "income".equals(s.getTransactionCategory()))
    .filter(s -> shippingOrderIds.contains(s.getOrderId()))
    .collect(Collectors.toList());
```

关联方式是 `shippingOrderIds.contains(orderId)`，即只判断订单号是否在配送集合中，不会因为配送有多行而重复拉取销售数据。

但销售数据本身也可能存在同一订单号多行的情况（同一订单不同 SKU 的结算记录）。这些行会被全部纳入 `incomeList`，然后逐行累加费用（sellingFees、fbaFees 等）。

**关键判断：这是正确的行为。** 亚马逊结算报告中，同一订单的不同 SKU 会生成独立的结算行，每行有各自的佣金、FBA 费用等。逐行累加不会重复。

**结论：销售数据关联不存在重复问题。**

### 4. 汇率映射（存在覆盖风险 ⚠️）

```java
// 构建 orderId -> exchangeRate 映射
if (shipping.getExchangeRate() != null) {
    orderRateMapBySite.computeIfAbsent(site, k -> new HashMap<>())
        .put(orderId, shipping.getExchangeRate());
}
```

使用 `HashMap.put()`，同一订单号的多行配送记录会互相覆盖汇率，最终保留最后一条的汇率值。

**风险评估：低风险。** 同一订单的多行配送记录通常在同一天发货（同一个 shipDate），因此汇率相同。即使分批发货（833 个订单），发货日期差异通常在 1-2 天内，汇率差异极小。

但严格来说，分批发货的订单可能跨天，汇率会有微小差异。当前逻辑取最后一条的汇率，而非加权平均或按 SKU 匹配。

**结论：汇率映射存在理论上的微小偏差，但实际影响可忽略。**

### 5. 退款关联（无重复风险 ✅）

退款数据的关联逻辑与收入数据一致，通过 `shippingOrderIds.contains(orderId)` 判断。退款记录本身也是按行独立的，逐行累加不会重复。

**结论：退款计算不存在重复问题。**

## 综合结论

| 计算环节 | 是否存在重复计算 | 说明 |
|---------|----------------|------|
| 收入总额（配送数据逐行累加） | ✅ 无重复 | 每行是独立 SKU 行项，金额不重叠 |
| 订单号集合（Set 去重） | ✅ 无重复 | HashSet 天然去重 |
| 销售数据关联（orderId 匹配） | ✅ 无重复 | 只判断订单号是否存在，不因配送多行而重复拉取 |
| 费用累加（income/refund 逐行） | ✅ 无重复 | 销售数据每行是独立结算记录 |
| 汇率映射（orderId → rate） | ⚠️ 微小偏差 | 同一订单多行配送会覆盖汇率，分批发货场景有微小差异 |
| 退款计算 | ✅ 无重复 | 与收入逻辑一致 |

**总结：报税汇总接口在配送数据修复（加入 SKU 去重维度）后，不会产生重复计算问题。**

原因：
1. 收入总额直接从配送数据逐行累加，每行是独立的 SKU 行项金额
2. 费用（佣金、FBA 费等）从销售数据获取，通过订单号 Set 关联，不受配送行数影响
3. 销售数据本身也是按 SKU 行项独立结算的，逐行累加是正确的

唯一的小瑕疵是汇率映射在分批发货场景下可能有微小偏差（833/116,677 = 0.7% 的订单），但对报税汇总金额的影响可忽略不计。
