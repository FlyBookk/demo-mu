# 结算数据推导需求讨论

## 一、背景

当前系统中结算单和INV的数据来源是 `t_settlement_import_data` 表，需要手动导入。但实际业务中，结算数据的单价是通过"采购成本 + FBA明细数据"推导出来的。

之前的数据是开发阶段通过推理预置的，后续需要将这个推导过程产品化，让财务人员可以自主操作。

---

## 二、核心推算流程（已确认）

```
① 选择结算周期（固定7天，周二到下周一）
        ↓
② 从 t_shipping_data 查询周期内配送记录，收集 orderId 集合
        ↓
③ 用 orderId 关联 t_sales_data，筛选 income/refund，汇总净销售数量（按站点+MSKU）
        ↓
④ 财务手动输入各站点采购成本（人民币金额）
        ↓
⑤ 系统查询该周期内各站点汇率平均值
        ↓
⑥ 采购成本（原币）= 采购成本（人民币）÷ 周期平均汇率
        ↓
⑦ MSKU单价 = 站点采购成本（原币）÷ 站点总净销售数量
        ↓
⑧ 展示列表（MSKU / 数量 / 单价 / 金额），财务可调整单价
        ↓
⑨ 确认后写入 t_settlement_import_data
        ↓
生成结算单 → 生成 INV
```

## 三、已确认需求点

### Q1：FBA明细数据的来源 ✅

**结论**：数量通过**配送数据推导销售数据**获得（与税务汇总模块逻辑一致），不是直接查询销售数据。

推导路径：
```
① 从 t_shipping_data 查询结算周期内（按 shipDate）的配送记录，收集 orderId 集合
② 用 orderId 集合关联 t_sales_data，筛选 income 类型，汇总各 MSKU 销售数量
③ 用 orderId 集合关联 t_sales_data，筛选 refund 类型，汇总各 MSKU 退款数量
④ 净销售数量 = income 数量 - refund 数量
```

按 **结算周期 + 站点 + MSKU** 三个维度汇总，与协议3.1一致：
> 以亚马逊卖家平台已完成订单数量为准，扣除对应周期内退货退款。

---

### Q2：单价分摊算法 ✅（已修正）

**结论**：系统先按等比分摊计算初始单价，财务再根据产品规格差异手动调整。

**数据分析发现**（108 份历史结算单）：
- 100% 的结算单中，同一站点同一周期内不同 MSKU 单价不同
- 单价差异核心规律：MSKU 变体编号（第 3 段）反映产品规格/尺寸
  - 短变体（1 位数：2、5、6、7 等）→ 低单价档
  - 长变体（2 位以上：20、25、206、209、268 等）→ 高单价档，约为短变体的 1.5 倍

**方案**：
```
① 初始单价 = 站点采购成本（原币）÷ 站点总净销售数量（等比分摊作为起点）
② 展示可编辑列表，财务根据产品规格差异手动调整各 MSKU 单价
③ 调整后金额自动重算：金额 = 数量 × 新单价
```

说明：
- 等比分摊仅作为初始值，财务必须根据实际产品规格调整单价
- 不同结算周期汇率不同，导致同一 MSKU 跨周期单价有波动，这是正常的业务现象
- 系统标记"初始值"和"已调整"状态，方便财务区分

---

### Q3：采购成本的粒度 ✅

**结论**：按站点输入人民币金额，共4个站点（USD/CAD/GBP/EUR）。

- 财务从报税汇总模块获取各站点采购成本（人民币）
- 采购成本参考公式：`采购成本 = 收入净额 − 平台支出合计 − 4%利润`
- 系统使用结算周期内的汇率平均值换算为原币

---

### Q4：结算周期选择 ✅

**结论**：固定7天周期（周二到下周一），与实际操作一致。

- 不支持自定义起止日期（避免产生重叠的结算数据，无法控制）
- 后续如有诉求再扩展
- 协议约定的"每自然月"与实际操作不一致，以实际操作为准

---

### Q5：数据覆盖策略 ✅

**结论**：新推导覆盖旧值，旧值逻辑删除，通过批次标识关联追溯。

核心机制：
1. **批次标识**：每次推导生成唯一的 `settlement_batch_id`，写入 `t_settlement_import_data` 的每条记录
2. **关联维度**：通过 **结算周期（起止日期）+ 站点** 唯一定位一批数据
3. **覆盖流程**：
   - 重复推导同一周期时，系统通过 周期+站点 查找已有数据
   - 旧数据逻辑删除（`del_flag = 1`），保留历史记录
   - 新数据写入，关联新的 `settlement_batch_id`
4. **可追溯性**：旧数据不物理删除，可通过 `del_flag` 和 `settlement_batch_id` 追溯历史推导记录

覆盖时的提示：
- 如果检测到同周期同站点已有数据，提示用户"该周期已有推导数据，确认覆盖？"
- 用户确认后执行覆盖（旧值逻辑删除 + 新值写入）

## 四、结算单与INV的关系（已确认）

结算单和INV是**完全对应的一对一关系**，数据完全相同：

| 维度 | 结算单 | INV |
|------|--------|-----|
| MSKU列表 | 完全相同 | 完全相同 |
| 数量/金额 | 完全相同 | 完全相同 |
| 日期 | 结算日（周二） | 结算日+1个工作日（通常周三） |
| 发起方 | 甲方→乙方 | 乙方→甲方 |
| 语言 | 简体中文+英文 | 全英文 |

两者差异仅在于日期差1个工作日、格式和视角不同。

---

## 五、影响范围（已确认）

本次结算数据推导功能**仅影响结算单和INV**，对PO和送货单没有任何调整。

| 单据类型 | 数据来源 | 是否受影响 |
|---------|---------|-----------|
| PO采购订单 | FBA货件数据（`t_fba_shipment`） | ❌ 不受影响 |
| 送货单 | FBA货件数据（`t_fba_shipment`） | ❌ 不受影响 |
| 结算单 | 销售数据 + 采购成本推算 → `t_settlement_import_data` | ✅ 本次调整 |
| INV发票 | 从结算单一对一生成 | ✅ 本次调整 |
