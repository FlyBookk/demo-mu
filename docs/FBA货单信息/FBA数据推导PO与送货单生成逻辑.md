# FBA数据推导PO与送货单生成逻辑

## 一、业务背景

根据《供货框架协议》（Hong Kong Andeo Group Limited - 东莞市慕声商贸有限公司），双方合作模式为"预采购→送货→实销实结"。整个单据链条如下：

```
PO采购订单 → 送货单 → 结算单 → INV发票
(预采购意向)   (到货确认)  (实销实结)  (付款依据)
 甲方→乙方     乙方→甲方    甲方→乙方   乙方→甲方
```

- 甲方（采购方）：东莞市慕声商贸有限公司
- 乙方（供货方）：Hong Kong Andeo Group Limited

本文档基于41份PO、9份送货单、108份结算单、108份INV以及FBA发货明细CSV的全量数据分析，推导PO和送货单的生成逻辑。

## 二、数据源分析

### 2.1 FBA发货明细（源数据）

CSV字段结构：

| 字段 | 说明 | 示例 |
|------|------|------|
| 货件单号 | FBA Shipment ID，唯一标识一次发货 | FBA15KS3Q60G |
| 货件名称 | 内部批次编号 | RP250828003 |
| 货件状态 | 货件当前状态 | CLOSED |
| 创建时间 | 货件在亚马逊后台创建的时间 | 2025-08-29 17:55 |
| 更新时间 | 货件最后更新时间（通常为签收完成时间） | 2025-11-15 03:09 |
| MSKU | 商家SKU编码 | MSUK-D70-5-4 |
| 申报量 | 发货时申报的商品数量 | 125 |
| 签收量 | 亚马逊仓库实际签收的数量 | 125 |
| 收件人 | FBA仓库收件方 | Amazon EU SARL (UK) |
| 物流中心编码 | FBA仓库编码 | BHX4 |
| 收件邮编/国家/州省/城市/街道/门牌号 | FBA仓库完整地址 | — |

CSV数据特点：
- 每个货件的第一行包含完整信息（货件单号、名称、状态、时间、地址等）
- 后续行仅包含MSKU、申报量、签收量，其余字段为空
- 需要将后续行自动关联到最近一个非空货件单号
- 当前CSV仅包含英国站第三季度数据（7个货件），不是全量数据

## 三、核心发现：PO与送货单的关系

### 3.1 货件ID 100%重叠

对全量数据（41份PO、9份DN）的交叉分析结果：

| 指标 | 数值 |
|------|------|
| PO中唯一货件ID数 | 101 |
| DN中唯一货件ID数 | 101 |
| 共有货件ID数 | 101 |
| PO独有 | 0 |
| DN独有 | 0 |
| **重叠率** | **100%** |

### 3.2 MSKU和数量完全一致

对101个共有货件逐一对比：

| 指标 | 数值 |
|------|------|
| MSKU列表+数量完全匹配 | 101/101 |
| MSKU列表不同 | 0 |
| 数量不同 | 0 |
| **匹配率** | **100%** |

### 3.3 结论

PO和送货单包含完全相同的货件数据（相同的货件ID、相同的MSKU列表、相同的数量）。两者的区别仅在于：

| 维度 | PO采购订单 | 送货单 |
|------|-----------|--------|
| 发起方 | 甲方（买方） | 乙方（供应商） |
| 语言 | 简体中文+英文 | 繁体中文+英文 |
| 日期 | PO生成日期（事件驱动） | 送货日期（批量确认） |
| 模板格式 | 含FBA仓库地址 | 含货件编号备注 |
| 生成频率 | 高频（每周1-3份） | 低频（约每3周1份） |

之前文档中"PO用申报量、送货单用签收量"的结论是错误的。实际上两者使用完全相同的数量。

## 四、PO采购订单生成逻辑

### 4.1 协议依据

> 协议1.2：甲方根据销售预测及亚马逊FBA货件创建情况，向乙方下达《PO》，作为供货指令。

### 4.2 PO日期规律

| 统计项 | 数值 |
|--------|------|
| 总PO数 | 41份 |
| 日期范围 | 2025/3/5 - 2025/9/2 |
| 最常见星期 | 周二（19次，占46%） |
| 其次 | 周一(7次)、周四(6次)、周五(6次)、周三(3次) |
| 周末 | 0次 |

PO日期不是固定周期，而是事件驱动（FBA货件创建后触发）。从6月起，周二生成PO的比例明显增高，与结算周期的结算日（周二）趋于一致。

每周PO数量：1-3份不等，取决于该周创建的FBA货件数量。

### 4.4 生成规则

1. **触发条件**：FBA货件创建后，按批次生成PO（非固定周期）
2. **数据来源**：FBA货件数据（货件编号、MSKU、数量、FBA仓库地址）
3. **明细组织**：
   - 按货件编号分组，每个货件下列出所有MSKU
   - 同一货件的第一个MSKU行在D列填写FBA仓库完整收货地址
   - 同一货件的后续MSKU行D列留空
   - 地址格式：`{街道地址}, {城市}, {州省}, {邮编}, {国家}`
4. **多站点合并**：一份PO可包含多个国家站点的货件（UK/CA/EU/US）
5. **编号规则**：`{YYYYMMDD}{3位序号}`，日期为PO生成日期，序号当日自增（通常为001）
6. **尾部合计**：所有MSKU数量之和

### 6.4 结算单生成规则

1. **周期**：每7天一个结算周期（周二到下周一）
2. **结算日**：周期结束后的第一天（周二）
3. **拆分**：每个周期按站点/货币拆分为4份（USD/CAD/GBP/EUR）
4. **数据**：该周期内各站点的实际销售数据（MSKU、数量、单价、金额）
5. **编号**：`{YYYYMMDD}{3位序号}`，001-004对应四个站点

### 6.5 INV发票

INV与结算单是同一份数据的不同格式：

| 维度 | 结算单 | INV |
|------|--------|-----|
| 日期 | 结算日（周二） | 结算日+1个工作日（通常周三） |
| 发起方 | 甲方→乙方 | 乙方→甲方 |
| 语言 | 简体中文+英文 | 全英文 |
| MSKU列表 | 完全相同 | 完全相同 |
| 数量/金额 | 完全相同 | 完全相同 |
| 买方名称 | 东莞市慕声商贸有限公司 | Dongguan Musheng Trade Co., Ltd. |
| 卖方名称 | Hong Kong Andeo Group Limited | Hong Kong Andeo Group Limited |
| 额外信息 | 签章确认栏 | 供应商银行信息 |

INV日期特殊情况：当结算日+1天遇到周末或节假日时，INV日期顺延到下一个工作日。例如20260102（周五）的结算单，对应INV日期为20260105（周一），跳过了周末。

### 6.7 INV生成规则

1. **数据来源**：与对应结算单完全相同的MSKU、数量、单价、金额
2. **日期规则**：结算日+1个工作日（跳过周末和节假日）
3. **编号规则**：`{YYYYMMDD}{3位序号}`，001-004对应四个站点
4. **货币标识**：H11列标题随站点变化（Total(USD)/Total(CAD)/Total(GBP)/Total(EUR)）
5. **合计行格式**：`CIF {货币}` + `TOTALS ({货币})` + 总数量 + 总金额
6. **银行信息**：固定在明细之后，包含Account name、account number、Bank Name、Bank address、Swift Code
7. **语言**：全英文（供应商视角的商业发票）

### 6.8 与协议条款的差异

> 协议3.2：按每自然月为一个结算周期

实际操作中结算频率为每7天，比协议约定的"每自然月"更频繁。

## 七、完整单据链时间线

```
FBA货件创建 ──→ PO生成 ──→ 送货单确认 ──→ 亚马逊销售 ──→ 结算单 ──→ INV
                                                         
时间示例:
2025/8/29    2025/9/2    2025/10/22    持续销售中    每周二    每周三
(货件创建)   (PO日期)    (DN日期)                   (7天周期)  (结算日+1)
             ← 4天 →    ← 50天 →                   
```

PO到DN的时间差约50-80天，反映了从采购下单到批量确认收货的完整周期。

## 九、生成流程总结

### 9.1 PO采购订单生成流程

```
输入: FBA货件数据

步骤1: 获取待生成PO的FBA货件列表
步骤2: 对每个货件，提取所有MSKU和数量
步骤3: 按货件分组，组装PO明细（货件编号 + MSKU + 数量 + FBA仓库地址）
步骤4: 生成PO编号（{YYYYMMDD}001）
步骤5: 按模板输出Excel文件（简体中文+英文）

输出: PO Excel文件
```

### 9.2 送货单生成流程

```
输入: 已生成的PO数据（或相同的FBA货件数据）

步骤1: 收集待确认的货件列表（约3周批量一次）
步骤2: 将所有货件的MSKU展开为逐行明细
步骤3: 每行标注对应的货件编号（备注列）
步骤4: 生成送货单编号（{YYYYMMDD}001）
步骤5: 按模板输出Excel文件（繁体中文+英文）

输出: 送货单 Excel文件
```

### 9.3 结算单生成流程

```
输入: 亚马逊销售数据 + 结算周期（7天）

步骤1: 确定结算周期（周二到下周一）
步骤2: 汇总该周期内各站点的销售数据
步骤3: 按站点拆分为4份（USD/CAD/GBP/EUR）
步骤4: 计算每个MSKU的销售数量、单价、金额
步骤5: 生成结算单编号（{YYYYMMDD}{001-004}）
步骤6: 按模板输出Excel文件
```

## 十一、结算单数据来源与单价推算（已确认）

### 11.1 结算单数量来源

结算单的数量通过**配送数据推导销售数据**获得（与税务汇总模块逻辑一致），不是直接查询销售数据。

推导路径：
```
① 从 t_shipping_data 查询结算周期内（按 shipDate）的配送记录，收集 orderId 集合
② 用 orderId 集合关联 t_sales_data，筛选 transactionCategory = 'income'，汇总各 MSKU 销售数量
③ 用 orderId 集合关联 t_sales_data，筛选 transactionCategory = 'refund'，汇总各 MSKU 退款数量
④ 净销售数量 = income 数量 - refund 数量
```

按结算周期 + 站点 + MSKU 三个维度汇总，与协议3.1一致：
> 以亚马逊卖家平台已完成订单数量为准，扣除对应周期内退货退款。

### 11.2 结算单单价来源（已确认推算逻辑，已修正分摊方案）

单价**不是**亚马逊销售价格，而是通过"采购成本分摊"推算得出：

**第一步：财务输入采购成本（人民币）**
- 财务人员从报税汇总模块获取各站点的采购成本（`procurementCostCny`，人民币）
- 采购成本计算公式：`采购成本 = 收入净额 − 平台支出合计 − 4%利润`

**第二步：人民币换算为原币**
- 使用该结算周期内的**汇率平均值**进行换算
- `采购成本（原币）= 采购成本（人民币）÷ 结算周期平均汇率`
- 不同结算周期汇率不同 → 导致同一MSKU在不同周期单价有波动（这是正常的，反映了汇率变化）

**第三步：计算初始单价（等比分摊）**
- `MSKU初始单价 = 站点采购成本（原币）÷ 站点总净销售数量`
- 等比分摊仅作为初始值，不是最终单价

**第四步：财务手动调整单价**
- 系统推算结果展示为可编辑列表，初始单价标记为"初始值"
- 财务根据产品规格差异调整各MSKU单价（历史数据显示长变体约为短变体的1.5倍）
- 调整后标记变为"已调整"，金额自动重算：`金额 = 数量 × 单价`

**数据分析发现**（108份历史结算单）：
- 100%的结算单中，同一站点同一周期内不同MSKU单价不同
- MSKU变体编号（第3段）反映产品规格/尺寸，决定了单价档位
- 短变体（1位数：2、5、6、7等）→ 低单价档
- 长变体（2位以上：20、25、206、209、268等）→ 高单价档，约为短变体的1.5倍

### 11.3 单价波动与差异的业务含义

**同一周期内不同MSKU单价不同**，原因：
1. **产品规格差异**：MSKU变体编号反映了产品规格/尺寸，不同规格的产品成本不同
2. **财务手动调整**：财务根据产品实际成本差异调整各MSKU单价

**同一MSKU跨周期单价不同**，原因：
1. **汇率变化**：每个结算周期使用该周期内的平均汇率换算，汇率波动直接影响原币单价
2. **采购成本变化**：不同周期的销售结构、平台费用、广告费用不同，导致采购成本总额变化
3. **销售数量变化**：分摊基数（总销售数量）不同，影响初始单价

这与历史数据分析结论一致（如MSUK-D70-5-4跨周期单价3.32-4.92 GBP的波动）。

### 11.4 完整推算流程

```
结算周期（起止日期）
        ↓
① 从 t_shipping_data 查询周期内配送记录，收集 orderId 集合，构建 orderRateMap
        ↓
② 用 orderId 关联 t_sales_data，筛选 income/refund，汇总净销售数量（按站点+MSKU）
        ↓
③ 财务手动输入各站点采购成本（人民币金额）
        ↓
④ 系统查询该周期内各站点汇率平均值
        ↓
⑤ 采购成本（原币）= 采购成本（人民币）÷ 周期平均汇率
        ↓
⑥ MSKU单价 = 站点采购成本（原币）÷ 站点总净销售数量
        ↓
⑦ 展示列表（MSKU / 数量 / 单价 / 金额），财务可调整单价
        ↓
⑧ 确认后写入 t_settlement_import_data
        ↓
生成结算单 → 生成 INV
```

## 十二、工作日处理规则（轻量化）

### 12.1 适用场景

以下日期计算需要考虑工作日：
- **结算日**：结算周期结束后的下一个工作日（通常为周二）
- **INV日期**：结算日+1个工作日（通常为周三）
- **DN日期**：如果计算出的日期是非工作日，顺延到下一个工作日

### 12.2 轻量化方案

精度要求"说的过即可"，采用最简方案：

1. **周末排除**：周六、周日为非工作日
2. **节假日列表**：硬编码一份年度主要节假日常量数组（`List<LocalDate>`），仅包含：
   - 元旦（1月1日）
   - 春节（约5-7天，按实际年份配置）
   - 清明节（1天）
   - 劳动节（1天）
   - 端午节（1天）
   - 中秋节（1天）
   - 国庆节（10月1-3日）
   - 圣诞节（12月25-26日）
3. **不做调休处理**：内地调休上班日按正常工作日处理
4. **每年手动更新**：年初在代码常量中更新当年日期即可，无需数据库表或管理界面

### 12.3 工作日判定算法

```
isWorkingDay(date):
  1. 如果是周六或周日 → 非工作日
  2. 如果在节假日常量列表中 → 非工作日
  3. 否则 → 工作日

nextWorkingDay(date):
  next = date + 1天
  while !isWorkingDay(next):
    next = next + 1天
  return next
```

## 十三、数据一致性与确定性要求

### 13.1 核心原则

**同一批输入数据，无论何时导出、导出多少次，所有输出结果必须完全一致。**

这是因为系统中的日期和部分数据是推算/估算值，不是精确值。如果每次导出使用不同的算法或随机因素，会导致同一批数据每次导出结果不同，造成业务混乱。

### 13.2 确定性要求清单

| 数据项 | 确定性规则 |
|--------|-----------|
| PO日期 | 基于FBA货件创建时间确定性推算，不使用当前时间 |
| PO编号 | 基于PO日期 + 固定排序规则生成序号 |
| DN日期 | 基于3周批量周期确定性计算 |
| DN编号 | 基于DN日期 + 固定排序规则生成序号 |
| 结算周期 | 基于固定的周二-周一规则确定性划分 |
| 结算日 | 基于结算周期结束日 + 工作日规则确定性计算 |
| INV日期 | 基于结算日 + 1工作日确定性计算 |
| 结算单/INV编号 | 基于结算日/INV日期 + 站点序号确定性生成 |
| MSKU排序 | 在同一单据内按固定规则排序（如字母序） |
| 金额计算 | 金额 = 数量 × 单价，使用精确计算（BigDecimal），不使用浮点数 |

### 13.3 实现要点

1. **禁止使用当前时间戳**：所有日期必须从输入数据推算，不依赖 `new Date()` 或 `System.currentTimeMillis()`
2. **固定排序规则**：所有列表输出必须有确定性的排序规则（如按MSKU字母序、按货件创建时间排序等）
3. **确定性编号生成**：编号的序号部分基于固定排序后的位置，而非数据库自增ID或随机数
4. **精确数值计算**：金额使用 BigDecimal，避免浮点精度问题
5. **工作日计算确定性**：基于固定的节假日配置表，不依赖外部API
6. **幂等性**：相同输入 → 相同输出，无副作用

### 13.4 PO日期推算规则（确定性）

基于数据分析，PO日期与FBA货件创建时间的关系：
- PO日期 = FBA货件创建时间所在周的下一个工作日（周二优先）
- 如果同一周有多个货件创建，合并到同一份PO
- 排序规则：按货件创建时间升序

### 13.5 DN日期推算规则（确定性）

- 以第一份DN日期（2025/5/22）为锚点
- 每隔21天（3周）生成一份DN
- DN日期 = 锚点 + N × 21天
- 如果计算出的日期是非工作日，顺延到下一个工作日
- 每份DN包含该周期内所有已有PO但尚未纳入DN的货件
