## 1. 文档概述

### 1.1 背景说明
广告模块原始数据格式发生变更，需要重新设计数据结构以支持新的业务需求。本文档基于最新的原始数据样例（`利润报表-广告发票记录-872100874146775040.xlsx`）进行分析，定义数据字段及其属性。

### 1.2 核心变更
1. **账单周期字段拆分**：原单一字段拆分为 `billing_start_date` 和 `billing_end_date` 两个独立字段
2. **数据去重机制**：基于发票编号（invoice_number）进行去重，默认保留第一条记录
3. **字段标准化**：统一字段命名规范和数据类型定义

### 1.3 数据样本分析结果
- **样本数据量**: 32条记录
- **唯一发票数**: 3个
- **重复记录数**: 29条（去重率：90.6%）
- **字段数量**: 18个
- **数据完整性**: 100%（无空值）

## 4. 数据处理规则

### 4.1 数据去重规则

#### 4.1.1 去重逻辑
- **去重字段**: `invoice_number`（发票编号）
- **去重策略**: 保留第一条记录，丢弃后续重复记录
- **实施位置**: 后端数据导入层（Service层）

#### 4.1.2 去重实现伪代码
```
输入: 原始数据列表 (List<AdvertisingData>)
输出: 去重后数据列表

1. 创建 Map<String, AdvertisingData> uniqueMap (LinkedHashMap保证顺序)
2. 遍历原始数据列表:
   a. 获取当前记录的 invoice_number
   b. 如果 uniqueMap 中不存在该 invoice_number:
      - 将该记录加入 uniqueMap (key=invoice_number, value=记录)
   c. 如果已存在:
      - 跳过该记录，记录日志（可选）
3. 返回 uniqueMap.values() 作为去重后的列表
```

#### 4.1.3 去重效果预估
根据样本数据分析：
- 样本记录数：32条
- 去重后记录：3条
- 去重率：90.6%
- 实际业务中去重率可能较低，建议在导入前向用户展示去重预览

### 4.2 账单周期字段处理

#### 4.2.1 原始格式
- 格式：`YYYY-MM-DD至YYYY-MM-DD`
- 示例：`2025-06-30至2025-07-03`
- 分隔符：`至`

#### 4.2.2 拆分逻辑
```
输入: 账单周期字符串 (如 "2025-06-30至2025-07-03")
输出: (billing_start_date, billing_end_date)

1. 使用 "至" 作为分隔符拆分字符串
2. 取第一部分作为 billing_start_date
3. 取第二部分作为 billing_end_date
4. 转换为日期类型
5. 校验：billing_start_date <= billing_end_date
```

#### 4.2.3 数据校验规则
| 校验项 | 规则 | 错误提示 |
|-------|------|---------|
| 日期格式 | 必须为 YYYY-MM-DD | "日期格式不正确，应为YYYY-MM-DD" |
| 开始≤结束 | billing_start_date <= billing_end_date | "账单开始日期不能晚于结束日期" |
| 非空校验 | 两个字段均不能为空 | "账单日期不能为空" |
| 合理性校验 | 日期范围不超过1个月 | "账单周期异常，超过31天"（警告） |

### 4.3 数据类型转换

| 原始类型 | 目标类型 | 转换规则 | 异常处理 |
|---------|---------|---------|---------|
| String (日期) | DATE | 解析 YYYY-MM-DD 格式 | 格式错误时拒绝导入 |
| String (数字) | DECIMAL | 保留2位小数 | 非数字时拒绝导入 |
| String (整数) | INT | 转换为整数 | 非整数时拒绝导入 |
| String | VARCHAR/TEXT | 直接存储 | 长度超限时截断并告警 |

### 4.4 数据完整性校验

#### 4.4.1 必填字段校验
以下字段不允许为空：
- 店铺（store_name）

- 账单结束日期（billing_end_date）
- 开具时间（issue_date）

- 账单金额（invoice_amount）
- 费用（cost）

#### 4.4.2 数据合理性校验
| 字段 | 校验规则 | 处理方式 |
|------|---------|---------|
| 账单金额 | > 0 | 拒绝导入 |
| 费用 | >= 0 | 拒绝导入 |
| 点击 | >= 0 | 拒绝导入 |
| 平均点击单价 | >= 0 | 拒绝导入 |

## 6. 数据迁移方案

### 6.1 历史数据处理

如果系统中存在历史广告数据，需要进行数据迁移：

#### 6.1.1 迁移前准备
1. 备份原有广告数据表
2. 确认历史数据的账单周期字段格式
3. 编写数据迁移脚本

#### 6.1.2 迁移策略
```sql
-- 假设旧表中账单周期字段为 billing_period (格式: "2025-06-30至2025-07-03")

-- 方案一：原地修改（需停机维护）
ALTER TABLE advertising
  ADD COLUMN billing_start_date DATE AFTER payment_type,
  ADD COLUMN billing_end_date DATE AFTER billing_start_date;

UPDATE advertising
SET
  billing_start_date = STR_TO_DATE(SUBSTRING_INDEX(billing_period, '至', 1), '%Y-%m-%d'),
  billing_end_date = STR_TO_DATE(SUBSTRING_INDEX(billing_period, '至', -1), '%Y-%m-%d');

-- 验证迁移结果
SELECT COUNT(*) FROM advertising WHERE billing_start_date IS NULL OR billing_end_date IS NULL;

-- 如果验证通过，删除旧字段
ALTER TABLE advertising DROP COLUMN billing_period;

-- 方案二：创建新表并迁移（推荐，无需停机）
-- 略（见数据库DDL脚本）
```

### 6.2 数据一致性校验
迁移后需校验：
1. 记录总数是否一致
2. billing_start_date 和 billing_end_date 是否都有值
3. billing_start_date <= billing_end_date
4. 发票编号唯一性

## 9. 风险提示

### 9.1 数据质量风险
- **风险**: 原始数据可能包含大量重复记录
- **影响**: 导入后实际记录数远少于原始数据
- **应对**:
  - 导入前展示去重预览
  - 明确告知用户去重规则
  - 记录被去重的数据日志

### 9.2 日期格式风险
- **风险**: 不同来源的数据可能使用不同的日期格式
- **影响**: 日期解析失败，导入失败
- **应对**:
  - 提供多种日期格式支持（YYYY-MM-DD, YYYY/MM/DD等）
  - 日期校验失败时给出清晰的错误提示

### 9.3 历史数据迁移风险
- **风险**: 迁移脚本执行失败或数据丢失
- **影响**: 历史数据无法使用
- **应对**:
  - 迁移前完整备份数据
  - 在测试环境充分验证迁移脚本
  - 提供回滚方案

## 10. 附录

### 10.1 字段枚举值说明

#### 10.1.1 发票状态（invoice_status）
- `PAID_IN_FULL`: 已全额支付
- `UNPAID`: 未支付
- `PARTIALLY_PAID`: 部分支付
- `CANCELLED`: 已取消

#### 10.1.2 支付类型（payment_type）
- `CREDIT_CARD`: 信用卡
- `DEBIT_CARD`: 借记卡
- `BANK_TRANSFER`: 银行转账
- `OTHER`: 其他

#### 10.1.3 币种（currency）
