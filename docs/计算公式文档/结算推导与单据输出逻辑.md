# 结算推导与单据输出逻辑文档

> 版本：2026-03-21  
> 作者：wanhua

---

## 一、整体流程概览

```
销售数据导入
    ↓
结算推导（SettlementDerivationService）
    ├── 汇总净销售数量（SalesDataAggregator）
    ├── 查询平均汇率（ExchangeRateMapper）
    ├── 按 SKU 差异化定价（权重模型）
    └── 写入 t_settlement_import_data
    ↓
生成结算单（DocumentGenerateService → SettlementGenerator）
    ├── 从 t_settlement_import_data 读取推导结果
    ├── 按自然月拆分周期
    ├── 按站点分组（US/CA/UK/DE）
    ├── MSKU 去重汇总 + 字母升序
    └── 写入 t_document_settlement + t_document_settlement_item
    ↓
生成 INV（DocumentGenerateService → InvGenerator）
    ├── 基于结算单数据
    ├── INV 日期 = 结算日 + 3 个工作日
    ├── 复制 MSKU/数量/单价/金额
    └── 写入 t_document_inv + t_document_inv_item
```

## 二、销售数据汇总（SalesDataAggregatorImpl）

### 2.1 双路径汇总模型

净销售数量通过两条独立路径汇总后合并：

```
Income 路径（按配送日期）：
  t_shipping_data（shipDate 在周期内）
      → 收集 orderId 集合
      → 关联 t_sales_data（transactionCategory = income）
      → 按 siteCode + sku 累加数量

Refund 路径（按结算日期）：
  t_sales_data（transactionDate 在周期内，transactionCategory = refund）
      → 按 siteCode + sku 累减数量

合并：netSalesMap = incomeMap + refundMap（同 siteCode + sku 相加）
```

### 2.2 汇率回退策略

退款记录的汇率按以下优先级确定：

1. 从 Income 路径的 `orderRateMap`（配送数据中的汇率）获取
2. 回退到退款记录自身的 `exchangeRate` 字段
3. 都为空时记录 warn 日志

### 2.3 供应商结差退款汇总

对 `isSupplierMsku(sku) = true` 的退款记录（MSKU 前缀为 `MSUS-`、`MSCA-`、`MSUK-`、`MSEU-`、`MS-`），按 `siteCode + sku` 分组汇总：

- `quantity`：退款数量绝对值累加
- `amount`：退款金额（`total` 字段绝对值）累加，汇率为 null 时跳过金额
- `exchangeRate`：取最新一条有效汇率

### 2.4 输出结构（AggregationResult）

| 字段 | 类型 | 说明 |
|------|------|------|
| `netSalesMap` | `Map<siteCode, Map<sku, quantity>>` | 各站点各 MSKU 净销售数量 |
| `orderRateMap` | `Map<orderId, exchangeRate>` | 订单汇率映射（income 优先） |
| `supplierRefundMap` | `Map<siteCode, Map<sku, SupplierRefundDetail>>` | 供应商结差退款汇总 |

## 三、结算推导（SettlementDerivationServiceImpl）

### 3.1 入口：derive()

**请求参数（DerivationRequest）：**

| 字段 | 说明 |
|------|------|
| `startQuarter` | 起始季度，格式 `yyyy-Qn`，如 `2025-Q3` |
| `endQuarter` | 结束季度，格式 `yyyy-Qn` |
| `siteCosts` | 各站点采购成本列表（`siteCode` + `costCny` 人民币金额） |

**季度解析规则：**

| 季度 | periodStart | periodEnd |
|------|-------------|-----------|
| 2025-Q1 | 2025-01-01 | 2025-03-31 |
| 2025-Q2 | 2025-04-01 | 2025-06-30 |
| 2025-Q3 | 2025-07-01 | 2025-09-30 |
| 2025-Q4 | 2025-10-01 | 2025-12-31 |

### 3.2 差异化定价（权重模型）

核心思路：同一站点的总采购成本固定，按 SKU 的产品系列和尺码分配不同单价。

**Step 1：计算加权总量**

```
加权总量 = Σ（数量 × SKU权重）
SKU权重 = 产品系列权重 × 尺码系数
```

**产品系列权重（SERIES_WEIGHT_MAP）：**

| 系列 | 权重 | 定位 |
|------|------|------|
| D70 | 0.75 | 走量基础款 |
| D71 | 0.80 | 基础款升级 |
| D60 | 0.85 | 轻量款 |
| D30 | 0.90 | 经济款 |
| D33 | 0.95 | 经济款 |
| D72 | 1.00 | 标准款（基准） |
| D22 | 1.10 | 中端常规款 |
| D73 | 1.10 | 标准升级款 |
| D23 | 1.05 | 中端常规款 |
| D06 | 1.15 | 中高端款 |
| D25 | 1.20 | 中高端款 |
| D28 | 1.25 | 高端款 |
| D42 | 1.30 | 高端精品款 |
| D47 | 1.35 | 高端精品款 |
| D63 | 1.40 | 旗舰款 |
| D74 | 1.45 | 旗舰高端款 |
| D75 | 1.50 | 顶级旗舰款 |

**尺码系数（SIZE_FACTOR_MAP）：**

| 尺码标识（SKU末位数字） | 系数 |
|----------------------|------|
| 1 | 0.85 |
| 2 | 0.90 |
| 3 | 0.95 |
| 4 | 1.00（默认） |
| 5 | 1.08 |
| 6 | 1.15 |
| 7 | 1.22 |

**SKU 解析规则：**
- 系列：取 SKU 按 `-` 分割后第二段，匹配 `D\d+` 格式（如 `MS-D06-348-5` → `D06`）
- 尺码：取 SKU 最后一个字符，若为数字则使用，否则默认 `4`

**Step 2：计算基准单价**

```
基准单价（原币）= 总采购成本（原币）/ 加权总量
总采购成本（原币）= 采购成本（CNY）/ 平均汇率
```

**Step 3：计算各 SKU 单价**

```
SKU单价 = 基准单价 × SKU权重（保留2位小数，HALF_UP）
SKU金额 = SKU单价 × 数量（保留2位小数，HALF_UP）
```

### 3.3 平均汇率计算

从 `t_exchange_rate` 查询周期内（`rateDate` 在 `periodStart ~ periodEnd`）的所有汇率记录，取算术平均值（保留6位小数）。

站点与货币映射：

| 站点 | 货币 |
|------|------|
| US | USD |
| CA | CAD |
| UK | GBP |
| DE | EUR |

### 3.4 数据持久化

推导结果写入 `t_settlement_import_data`，写入前先逻辑删除同周期同站点的旧数据：

| 字段 | 说明 |
|------|------|
| `shopId` | 店铺ID（数据隔离） |
| `periodStart` / `periodEnd` | 结算周期 |
| `siteCode` | 站点代码（US/CA/UK/DE） |
| `currency` | 货币代码 |
| `msku` | SKU编码 |
| `quantity` | 净销售数量 |
| `unitPrice` | 差异化单价（原币） |
| `amount` | 金额（原币） |
| `procurementCostCny` | 站点总采购成本（CNY） |
| `averageExchangeRate` | 周期平均汇率 |
| `settlementBatchId` | 本次推导批次ID（UUID） |

### 3.5 确认接口：confirm()

用户在前端调整推导结果后，通过 `confirm()` 接口将最终数据写回 `t_settlement_import_data`。支持 `overwrite = true` 时先删除旧数据再写入。

## 四、结算单生成（SettlementGenerator）

### 4.1 输入（SettlementInput）

从 `t_settlement_import_data` 查询对应周期和站点的推导数据，构建 `SettlementInput`：

| 字段 | 说明 |
|------|------|
| `periodStart` / `periodEnd` | 结算周期 |
| `items` | 明细列表（siteCode、msku、currency、unitPrice、quantity、transactionDate） |

### 4.2 按自然月拆分

将大周期按自然月拆分，每个自然月生成一批结算单：

```
例：periodStart=2025-07-01, periodEnd=2025-09-30
→ 7月（2025-07-01 ~ 2025-07-31）
→ 8月（2025-08-01 ~ 2025-08-31）
→ 9月（2025-09-01 ~ 2025-09-30）
```

每月的数据过滤规则：
- 有 `transactionDate` 的记录：按日期归入对应月
- 无 `transactionDate` 的记录：归入当前处理月

### 4.3 结算日计算

```
结算日 = 下个月 5 日（非工作日则顺延至最近工作日）
例：7月数据 → 结算日 = 2025-08-05（若为工作日）
```

### 4.4 按站点分组

站点匹配优先级：
1. 优先用 `siteCode` 字段匹配货币代码（USD/GBP/CAD/EUR）
2. 再尝试匹配站点名称（US/UK/CA/DE）
3. 回退到 MSKU 前缀匹配（MSUS-→US，MSCA-→CA，MSUK-→UK，MSEU-→DE）

每个自然月固定生成 4 份结算单（US/CA/UK/DE），无数据的站点 `totalQuantity = 0`（生成后会被过滤掉）。

### 4.5 MSKU 汇总规则

同一站点内相同 MSKU 的记录：
- `quantity` 累加
- `unitPrice` 取第一条记录的值
- 最终按 MSKU 字母升序排列

### 4.6 单据编号规则

```
编号格式：{YYYYMMDD}{3位序号}
例：结算日 2025-08-05，序号1 → "20250805001"
    结算日 2025-08-05，序号2 → "20250805002"
```

同一结算日的 4 份结算单序号为 001~004（按 SiteCode 枚举顺序）。

### 4.7 结算单主表字段

| 字段 | 说明 |
|------|------|
| `documentNo` | 单据编号（11位） |
| `settlementDate` | 结算日 |
| `periodStart` / `periodEnd` | 结算周期 |
| `siteCode` | 货币代码（USD/CAD/GBP/EUR） |
| `siteSequence` | 站点序号（SiteCode 枚举中的 sequence） |
| `buyerName` | 东莞市慕声商贸有限公司 |
| `buyerAddress` | 广东省东莞市虎门镇连升路82号虎门万达广场2栋606房 |
| `sellerName` | Hong Kong Andeo Group Limited |
| `totalQuantity` | 合计数量 |
| `totalAmount` | 合计金额（保留4位小数） |

## 五、INV 发票生成（InvGenerator）

### 5.1 触发方式

传入结算单 ID 列表，系统查询结算单及明细，调用 `InvGenerator.generate()` 生成对应 INV。

### 5.2 INV 日期计算

```
INV日期 = 结算日 + 3个工作日
例：结算日 2025-08-05（周二）→ INV日期 = 2025-08-08（周五）
```

### 5.3 数据复制规则

INV 明细直接从结算单明细复制：
- `lineNo`、`msku`、`quantity`、`unitPrice`、`amount` 完整复制
- `totalQuantity`、`totalAmount` 从结算单主表复制

### 5.4 INV 主表字段

| 字段 | 来源 |
|------|------|
| `documentNo` | DocumentNumberCalculator（INV日期 + 序号） |
| `invDate` | 结算日 + 3个工作日 |
| `siteCode` | 从结算单复制 |
| `siteSequence` | 从结算单复制 |
| `sellerName` / `sellerAddress` / `sellerPhone` | DocumentPartyProperties 配置 |
| `buyerName` / `buyerAddress` / `buyerPhone` | DocumentPartyProperties 配置 |
| `bankAccountName` / `bankAccountNumber` | DocumentPartyProperties 配置 |
| `bankName` / `bankAddress` / `swiftCode` | DocumentPartyProperties 配置 |
| `totalQuantity` / `totalAmount` | 从结算单复制 |

### 5.5 幂等处理

结算单和 INV 的持久化均使用 `DuplicateKeyException` 捕获实现幂等：重复单据号时返回已有记录，不报错。

## 六、工具类说明

### 6.1 DocumentNumberCalculator

```
编号 = yyyyMMdd（8位）+ 序号（3位补零）
有效序号范围：1 ~ 999
```

### 6.2 SettlementPeriodCalculator

按 7 天为一个周期划分日期范围（周二到下周一），每个周期的结算日为周期结束日之后的下一个工作日。（注：当前结算单生成使用自然月拆分，此工具类为早期设计，保留备用。）

### 6.3 WorkingDayCalculator

- `nearestWorkingDay(date)`：若为工作日则返回当天，否则顺延至下一个工作日
- `nextWorkingDay(date)`：返回 date 之后的下一个工作日（不含当天）
- `addWorkingDays(date, n)`：在 date 基础上加 n 个工作日

## 八、关键业务规则汇总

| 规则 | 说明 |
|------|------|
| 季度格式 | `yyyy-Qn`，Q1=1~3月，Q2=4~6月，Q3=7~9月，Q4=10~12月 |
| 站点货币 | US→USD，CA→CAD，UK→GBP，DE→EUR |
| 供应商 MSKU 前缀 | MSUS-、MSCA-、MSUK-、MSEU-、MS-（按长度从长到短匹配） |
| 结算日 | 自然月结束后下个月5日，非工作日顺延 |
| INV 日期 | 结算日 + 3个工作日 |
| 单据编号 | yyyyMMdd + 3位序号（001起） |
| 金额精度 | 结算单/INV 金额保留4位小数，单价保留2位小数 |
| 数据隔离 | 所有查询和写入均通过 `ShopContext.requireShopId()` 隔离店铺数据 |
| 幂等保障 | 重复单据号时捕获 `DuplicateKeyException`，返回已有记录 |
| 空结算单过滤 | `totalQuantity = 0` 的结算单不入库 |
