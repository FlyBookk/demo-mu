# 字段映射画布交互设计文档

## 1. 概述

### 1.1 背景

当前字段映射模板功能采用手动录入方式配置源字段与目标字段的映射关系。用户需要：
1. 手动输入源字段名（需要查看原始文件获取）
2. 手动输入目标字段名（需要了解数据库结构）
3. 逐条添加映射配置

这种方式存在以下问题：
- **操作繁琐**：需要反复查看文件和数据库字段
- **易出错**：手动输入字段名容易拼写错误
- **效率低**：无法批量操作，字段多时耗时较长
- **不直观**：无法清晰看到映射关系全貌

### 1.2 目标

重构字段映射交互，采用**可视化画布**方式：
1. 选择数据类型后**自动加载**数据库实体字段及描述
2. 通过**上传文件**自动解析获取源字段
3. 用户在画布上**拖拽/划线**建立映射关系
4. 支持**删除**多余字段
5. 未映射的目标字段可设置**默认值**
6. 提供**智能映射**辅助匹配

### 1.3 现状分析

项目中已存在 `FieldMappingCanvas` 画布组件（`src/components/business/FieldMappingCanvas`），具备基础的拖拽连线功能。本次设计将：
1. 整合画布组件到字段映射模板管理页面
2. 增加数据类型联动加载目标字段功能
3. 增加文件上传解析源字段功能
4. 完善默认值配置交互
5. 优化整体用户体验

## 3. 交互设计

### 3.1 数据类型联动

#### 交互流程

销售数据有两种不同格式来源（亚马逊原始数据 / ERP结算明细），字段结构差异较大，需要支持**子类型选择**。

```
用户选择数据类型
       │
       ├─→ 销售数据 ─→ 显示子类型选择 ─→ 原始数据 / ERP数据
       │
       ├─→ 配送数据 ─→ 无子类型，直接加载字段
       │
       ├─→ 广告数据 ─→ 无子类型，直接加载字段
       │
       └─→ 汇率数据 ─→ 无子类型，直接加载字段
       │
       ▼
┌─────────────────┐
│  调用后端API     │  GET /api/v1/config/field-mapping-templates/target-fields/{dataType}?subType={subType}
│  获取目标字段列表 │
└─────────────────┘
       │
       ▼
┌─────────────────┐
│  右侧目标字段列表 │
│  自动加载并显示   │
│  - 字段名        │
│  - 中文标签      │
│  - 字段描述      │
│  - 数据类型      │
│  - 是否必填      │
└─────────────────┘
```

#### 数据类型选择交互

```
┌─ 基础信息 ──────────────────────────────────────────────────────────┐
│                                                                     │
│  模板名称: [___________________]    站点: [DE ▼]                    │
│                                                                     │
│  数据类型: [销售数据 ▼]                                              │
│                                                                     │
│  ┌─ 数据来源 ─────────────────────────────────────────────────────┐│
│  │                                                                 ││
│  │  ○ 亚马逊原始数据                 ○ ERP结算明细                  ││
│  │    从亚马逊后台下载的交易报告         ERP系统导出的结算明细数据    ││
│  │    每行是一笔订单的完整金额信息       每行是一笔费用明细           ││
│  │    字段横向展开                       需按订单聚合行转列          ││
│  │                                                                 ││
│  └─────────────────────────────────────────────────────────────────┘│
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 数据类型与实体映射

| 数据类型 | 子类型 | 编码 | 对应数据库表 | 说明 |
|---------|-------|------|-------------|------|
| 销售数据 | 亚马逊原始数据 | SALES_ORIGINAL | t_sales_data | 亚马逊后台交易报告，金额字段横向展开 |
| 销售数据 | ERP结算明细 | SALES_ERP | t_sales_data | ERP导出数据，按交易类型纵向展开 |
| 配送数据 | - | SHIPPING | t_shipping_data | 配送记录 |
| 广告数据 | - | ADVERTISING | t_advertising_data | 广告投放数据 |
| 汇率数据 | - | RATE | t_exchange_rate | 汇率配置 |

#### 销售数据两种格式的字段差异

**亚马逊原始数据 (SALES_ORIGINAL)**：
- 每行 = 一笔订单的完整信息
- 金额字段横向展开（product_sales, shipping_credits, fba_fees 等并列）
- 表头可能是英文/德文（按站点区分）
- 文件前几行可能有说明性信息

**ERP结算明细 (SALES_ERP)**：
- 每行 = 一笔费用明细
- 一个订单对应多行，按交易类型拆分（Principal, Commission, FBAPerUnitFulfillmentFee 等）
- 需要按 (订单号+SKU) 聚合，进行行转列转换
- 中文表头
- 包含店铺、结算状态等额外字段

#### 目标字段信息展示

每个目标字段应显示：
- **字段名**：数据库字段名（如 `order_id`）
- **中文标签**：字段中文名（如 "订单ID"）
- **描述**：字段用途说明
- **数据类型**：string / number / datetime
- **是否必填**：必填字段用红色星号标记
- **映射状态**：已映射(绿色) / 未映射(灰色) / 有默认值(橙色)

**文件解析规则**：

1. **CSV文件**：
   - 自动检测分隔符（逗号、制表符、分号）
   - 自动检测编码（UTF-8、GBK、GB2312）
   - 跳过空行

2. **Excel文件**：
   - 默认读取第一个Sheet
   - 支持选择Sheet（如有多个）

3. **示例值获取**：
   - 读取表头下一行数据作为示例值
   - 最多显示30个字符，超出截断

**分隔符自动检测规则**：

| 优先级 | 分隔符 | 检测条件 |
|-------|--------|---------|
| 1 | Tab制表符 | 包含 `\t` 字符 |
| 2 | 逗号 | 包含 `,` 且逗号数量 > 2 |
| 3 | 分号 | 包含 `;` 且分号数量 > 2 |
| 4 | 竖线 | 包含 `\|` 且竖线数量 > 2 |
| 5 | 空格 | 以上都不匹配时，按连续空格分割 |

## 9. 待讨论事项

### 9.1 技术实现问题

1. **文件解析位置**
   - 方案A：前端解析（使用 xlsx.js / Papa Parse）
     - 优点：响应快，无需上传，隐私性好
     - 缺点：大文件可能卡顿，需要引入解析库
   - 方案B：后端解析（上传到服务器解析）
     - 优点：统一处理，编码检测更准确
     - 缺点：需要上传文件，网络开销
   - 方案C：混合方案（小文件前端，大文件后端）
   - **建议**：前端解析为主，项目已有 xlsx 依赖可复用

2. **粘贴解析实现**
   - 完全在前端实现即可，无需后端接口
   - 使用正则表达式按分隔符分割

3. **目标字段元数据来源**
   - 方案A：后端API返回（需要后端维护字段定义）
   - 方案B：前端硬编码（维护成本高）
   - 方案C：从数据库注释自动读取（需要后端支持）
   - **建议**：方案A + 方案C 结合，字段信息从实体类注解或数据库注释自动生成

4. **智能匹配算法**
   - 是否需要后端支持？
   - 是否需要保存匹配历史用于学习？

### 9.2 产品功能问题

1. **是否支持批量导入模板？**
   - 从已有模板批量复制
   - 从 JSON/Excel 导入模板配置

2. **是否支持字段转换器？**
   - 如：日期格式转换、数值单位转换
   - 当前设计未包含，后续可扩展

3. **是否支持多站点模板共享？**
   - 同一数据类型，不同站点是否可共用模板

4. **源字段信息是否需要持久化？**
   - 当前设计每次编辑需重新上传文件
   - 是否需要保存源字段结构供下次编辑时显示

5. **ERP数据聚合规则是否需要可配置？**
   - 当前设计中交易类型到金额字段的映射是固定的
   - 是否需要在画布上支持配置"交易类型→目标字段"的映射规则
   - 还是在后端固定处理，前端只做基础字段映射

6. **销售数据两种格式的模板是否需要分开管理？**
   - 方案A：统一为"销售数据"，通过子类型筛选
   - 方案B：作为两个独立的数据类型（SALES_ORIGINAL / SALES_ERP）
   - **当前采用方案A**，更直观
