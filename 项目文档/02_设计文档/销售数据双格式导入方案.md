# 销售数据双格式导入方案

## 一、数据分析

### 1.1 当前系统销售数据结构

系统使用 `t_sales_data` 表存储销售数据，核心字段包括：

| 字段 | 说明 |
|------|------|
| order_id | 订单号 |
| site_code | 站点编码(US/UK/DE/CA) |
| transaction_type | 交易类型（原始值） |
| transaction_category | 交易分类(income/refund/fee/adjustment/other) |
| transaction_date | 交易日期 |
| product_sales | 产品销售额 |
| selling_fees | 销售费用 |
| fba_fees | FBA费用 |
| total | 合计 |
| ... | 其他金额字段 |

### 1.2 数据源一：亚马逊原始数据（按国家分散）

**文件示例**：
- `慕声美国2025年第三季度交易联合报告CustomUnifiedTransaction.csv`
- `慕声英国2025年第三季度CustomTransaction.csv`
- `慕声德国2025年第三季度CustomTransaction.csv`
- `慕声加拿大2025年第三季度CustomTransaction.csv`

**数据特点**：

1. **每个国家单独文件**，需要用户手动选择站点
2. **有7-8行说明性header**，真正的表头在后面
3. **按国家语言区分表头**：
   - US/UK/CA: 英文（date/time, order id, product sales 等）
   - DE: 德文（Datum/Uhrzeit, Bestellnummer, Umsätze 等）
4. **每行是一笔订单的完整信息**，金额字段横向展开

**美国站表头示例**：
```
"date/time","settlement id","type","order id","sku","description","quantity","marketplace",
"account type","fulfillment","order city","order state","order postal","tax collection model",
"product sales","product sales tax","shipping credits","shipping credits tax","gift wrap credits",
"giftwrap credits tax","Regulatory Fee","Tax On Regulatory Fee","promotional rebates",
"promotional rebates tax","marketplace withheld tax","selling fees","fba fees","other transaction fees","other","total"
```

**英国站表头差异**：
- `postage credits` 代替 `shipping credits`
- `fulfilment` 代替 `fulfillment`
- 少 `account type` 字段
- 少 `Regulatory Fee` 相关字段

**德国站表头示例**：
```
"Datum/Uhrzeit","Abrechnungsnummer","Typ","Bestellnummer","SKU","Beschreibung","Menge",
"Marketplace","Versand","Ort der Bestellung","Bundesland","Postleitzahl","Steuererhebungsmodell",
```

### 1.3 数据源二：ERP汇总数据

**文件示例**：
- `结算中心-结算明细-872116414561021952.csv`

**数据特点**：

1. **多国家合并在一个文件**，每行有"国家"字段区分
2. **中文表头**，字段命名清晰
3. **每行是一笔费用明细**（行级粒度更细）
4. **一个订单对应多行**，按交易类型拆分（如 Commission、Principal、FBAPerUnitFulfillmentFee 等）
5. 包含更多业务字段：店铺、结算状态、转账状态

## 二、核心差异对比

| 对比维度 | 亚马逊原始数据 | ERP汇总数据 |
|---------|--------------|-------------|
| **文件数量** | 按国家分多个文件（也可能合并） | 多国家合并一个文件 |
| **表头语言** | 英文/德文（按国家） | 中文 |
| **数据粒度** | 一行=一笔订单完整信息 | 一行=一笔费用明细 |
| **金额字段** | 横向展开多列 | 单列金额+交易类型区分 |
| **站点识别** | 通过 `marketplace` 字段自动识别 | 通过"国家"字段自动识别 |
| **说明行** | 有7-8行说明性header | 无说明行 |
| **特有字段** | 地址信息(city/state/postal) | 店铺、结算/转账状态 |
| **唯一键** | order_id + sku + transaction_category | 订单号 + SKU + 交易类型(聚合后) |

#### 3.2.3 字段差异说明

| 差异点 | 说明 |
|-------|------|
| **UK站: postage credits** | 英国站使用 "postage credits" 代替 "shipping credits"，需映射到 shippingCredits |
| **UK站: fulfilment** | 英式拼写，对应美式 "fulfillment" |
| **DE站: 德语表头** | 所有字段使用德语命名，需要完整映射 |
| **US/CA: account type** | 仅美国和加拿大站有此字段，其他站点默认空 |
| **US/CA: Regulatory Fee** | 仅美国和加拿大站有监管费字段，欧洲站默认0 |
| **DE站: 数字格式** | 德国站使用逗号作小数点（如 1.234,56），需要特殊处理 |

| CA | Jul 1, 2025 12:58:35 a.m. PDT | MMM d, yyyy h:mm:ss a z (注意 a.m./p.m.) |
| UK | 30 Jun 2025 23:01:46 UTC | dd MMM yyyy HH:mm:ss z |

```java
    /**
     * 根据表头自动检测语言区域
     */
    public static String detectRegion(List<String> headers) {
        String firstHeader = headers.get(0).toLowerCase().trim();
        if (firstHeader.contains("datum")) {
            return "DE";
        }
        // 检查是否有英国特有字段
        for (String h : headers) {
            if (h.toLowerCase().contains("postage credits")) {
                return "UK";
            }
        }
        // 默认按美国处理（US/CA字段基本一致）
        return "US";
    }

        return switch (region) {
            case "DE" -> DE_MAPPING;
            case "UK" -> UK_MAPPING;
            default -> US_MAPPING;
        };
    }
```

### 3.3 亚马逊原始数据清洗流程

```
1. 检测文件编码（UTF-8/UTF-8 BOM）
2. 跳过说明行，定位真正的表头行（检测包含 date/time 或 Datum/Uhrzeit）
3. 根据表头语言自动判断区域（英文/德文），获取对应的表头映射配置
4. 解析每行数据，读取 marketplace 字段
5. 通过 marketplace 自动映射站点编码：
   - amazon.com → US
   - amazon.co.uk → UK
   - amazon.de → DE
   - amazon.ca → CA
6. 根据站点获取字段映射配置
7. 数值格式处理（德国站: 1.234,56 → 1234.56）
8. 日期格式处理（多种格式统一到 LocalDateTime）
9. 交易类型标准化（Order→income, Refund→refund, 等）
10. 直接生成 SalesData 记录
```

**注意**：同一个文件中可能包含多个站点的数据（如欧洲站的报告可能同时包含 UK/DE/FR 数据），系统会逐行识别站点。

### 3.4 ERP汇总数据清洗流程

```
1. 检测文件编码
2. 解析表头（中文字段名映射）
3. 按 (订单号 + 站点 + SKU) 分组
4. 对每个分组进行行转列聚合：
   - Principal → product_sales
   - Tax → product_sales_tax  
   - Commission → selling_fees (累加)
   - FBAPerUnitFulfillmentFee → fba_fees (累加)
   - ...其他交易类型映射
5. 根据"国家"字段自动设置站点编码
6. 计算 total（如果原数据无合计）
7. 生成 SalesData 记录
```

## 四、技术实现方案

### 4.1 整体设计思路

采用**模板化字段映射**方案，通过预置模板配置来支持不同格式的数据导入：

1. **预置映射模板**：为每个站点 + 数据类型组合预先创建字段映射模板
2. **导入流程**：用户依次选择 站点 → 数据类型 → 模板 → 上传 → 预览 → 导入
3. **灵活可配置**：用户可以在字段映射模块自定义模板，适应数据格式变化
4. **ERP数据聚合**：ERP数据导入时自动按订单维度进行行转列合并

### 4.2 前端改造

#### 4.2.1 导入流程步骤

```

│  选择站点  →  选择数据类型  →  选择模板  →  上传文件 → 预览确认 │
│  (US/UK..)    (原始/ERP)     (自动筛选)   (CSV/Excel) (提交导入)│
```

```java
@Service
public class ErpSettlementParser implements SalesDataParser {
    
    // 中文表头到标准字段的映射
    private static final Map<String, String> HEADER_MAPPING = Map.ofEntries(
        entry("结算编号", "settlementId"),
        entry("订单号", "orderId"),
        entry("店铺", "storeName"),
        entry("国家", "siteCode"),
        entry("配送方式", "fulfillment"),
        entry("来源", "source"),
        entry("MSKU", "msku"),
        entry("交易类型", "transactionType"),
        entry("结算时间", "transactionDate"),
        entry("币种", "currencyCode"),
        entry("金额", "amount"),
        entry("数量", "quantity"),
        entry("SKU", "sku"),
        entry("品名", "description")
    );
    
    @Override
    public List<SalesData> parse(MultipartFile file) {
        // 1. 解析CSV得到明细行列表
        List<ErpSettlementRow> rows = parseCsvRows(file);
        
        // 2. 按 (订单号 + 站点 + SKU) 分组
        Map<String, List<ErpSettlementRow>> grouped = rows.stream()
            .collect(Collectors.groupingBy(r -> 
                r.getOrderId() + "|" + r.getSiteCode() + "|" + r.getSku()));
        
        // 3. 聚合生成 SalesData
        return grouped.values().stream()
            .map(this::aggregateToSalesData)
            .collect(Collectors.toList());
    }
    
    private SalesData aggregateToSalesData(List<ErpSettlementRow> rows) {
        SalesData data = new SalesData();
        ErpSettlementRow first = rows.get(0);
        
        // 基础信息取第一行
        data.setOrderId(first.getOrderId());
        data.setSiteCode(first.getSiteCode());
        data.setSku(first.getSku());
        data.setDescription(first.getDescription());
        data.setTransactionDate(first.getTransactionDate());
        data.setCurrencyCode(first.getCurrencyCode());
        data.setFulfillment(first.getFulfillment());
        data.setQuantity(first.getQuantity());
        
        // 根据来源确定交易分类
        data.setTransactionCategory(mapSourceToCategory(first.getSource()));
        data.setTransactionType(first.getSource());
        
        // 金额按交易类型累加
        BigDecimal productSales = BigDecimal.ZERO;
        BigDecimal sellingFees = BigDecimal.ZERO;
        BigDecimal fbaFees = BigDecimal.ZERO;
        // ... 其他金额字段
        
        for (ErpSettlementRow row : rows) {
            switch (row.getTransactionType()) {
                case "Principal" -> productSales = productSales.add(row.getAmount());
                case "Tax" -> data.setProductSalesTax(
                    data.getProductSalesTax().add(row.getAmount()));
                case "Commission" -> sellingFees = sellingFees.add(row.getAmount());
                case "FBAPerUnitFulfillmentFee" -> fbaFees = fbaFees.add(row.getAmount());
                // ... 其他类型
            }
        }
        
        data.setProductSales(productSales);
        data.setSellingFees(sellingFees);
        data.setFbaFees(fbaFees);
        
        // 计算合计
        data.setTotal(calculateTotal(data));
        
        return data;
    }
}
```

## 六、风险与注意事项

### 6.1 数据质量风险

1. **ERP数据结算编号格式**：以单引号开头（如 `'LWCBH4OW1XWS`），需要清理
2. **金额精度**：ERP数据金额小数位可能不一致，统一保留2位
3. **日期格式**：ERP格式 `2025-09-30 23:59:08`，需确保正确解析时区

### 6.2 性能风险

1. **ERP文件较大**：示例文件34万行，需要分批处理
2. **行转列聚合**：内存消耗较大，考虑流式处理或分批聚合

### 6.3 兼容性风险

1. **原有亚马逊原始数据导入逻辑保持不变**
2. **通过 sourceType 参数区分，默认值为 AMAZON_ORIGINAL 保证向后兼容
